# Поточні витрати підприємства

Архів містить лише 8 нових / змінених файлів до версії з оплатами закупівель (V87).

## Встановлення
1. Зробіть резервну копію БД та поточних сорсів.
2. Скопіюйте вміст backend/ у корінь бекенду, frontend/ — у корінь Vue-проєкту.
3. Нова міграція — V88__cash_expenses.sql. Раніше застосовані V84–V87 не змінюйте. Якщо V88 вже зайнята вашою власною міграцією, новому файлу призначте наступний вільний номер ДО першого запуску.
4. На бекенді виконайте:
   .\gradlew.bat test --tests "com.example.baget.cash.*"
5. На фронтенді виконайте npm run build та оновіть розгорнутий фронтенд. Запустіть бекенд, щоб Flyway застосував V88.

## Де знайти
Каси та рахунки → Витрати. Доступ: адміністратор, бухгалтер (включно з чинними ROLE_ACCOUNTANT, ROLE_BOOKKEEPER, ROLE_COUNTER). Менеджер не може читати журнал витрат або проводити / сторнувати витрати через цей API. Для кас філій діють allowedBranches; центральна каса та банківські рахунки доступні фінансовим ролям.

Категорії: оренда, комунальні послуги, ремонт устаткування, господарські витрати, інші поточні витрати. Виберіть касу / рахунок, дату платежу, суму, отримувача, призначення; номер документа необов’язковий. Підтвердіть, що кошти сплачено й операція ще не зареєстрована.

## Проведення й джерело сум
Сума зберігається у ledger_entries: OUT / OVERHEAD_EXPENSE з посиланням cash_expense_id. cash_expenses зберігає метадані, без дублювання фінансової суми. Витрата одразу зменшує залишок. Недостатній залишок блокує проведення. Не можна витрачати кошти в дорозі, із неініціалізованої каси або каси філії посередника.

Усі записи виконуються в одній транзакції, спільне блокування cash_control захищає перевірку залишку. requestKey захищає від повторного списання. Після мережевої помилки кнопка «Перевірити / повторити» повторює незмінний запит із тим самим ключем; він зберігається в sessionStorage й відновлюється після оновлення сторінки в тій самій вкладці.

Дата платежу зберігається окремо від часу реєстрації. Проводка ledger створюється поточним часом, тому попередні касові звірки не переписуються. Дата платежу не може бути майбутньою або передувати дню встановлення початкового залишку. Навіть за той самий день не вводьте повторно платіж, вже врахований у початковому залишку.

## Сторнування
У журналі натисніть «Сторнувати помилковий запис», вкажіть причину й підтвердіть, що кошти фактично залишились у касі / на рахунку. Створюється новий запис REVERSAL та IN / OVERHEAD_EXPENSE на повну початкову суму в тій самій касі. Початковий запис залишається. Повторне сторнування або сторнування самого сторно заборонено. Для виправлення суми сторнуйте помилковий запис і внесіть правильний. Реальне повернення коштів від постачальника — окрема операція, цей етап її не реалізує.

## Журнал і підсумки
Фільтри: період, каса / рахунок, категорія. Підсумки охоплюють всі записи за фільтром, а не лише поточну сторінку (50 записів). Суми читаються з ledger_entries. Витрати відбираються за датою платежу, сторно — за поточною датою його проведення. Якщо сторно стосується давнього платежу за межами періоду, підсумок періоду може бути від’ємним. У картках показані номер запису, отримувач, призначення, документ, користувач і час реєстрації.

Закупівлі / доставка залишаються в «Оплатах закупівель», винагороди менеджерів — у виплатах винагород. Не дублюйте їх тут. Витрати цього модуля не змінюють складську собівартість, Parts.Cost, залишки матеріалів, аванси клієнтів чи заборгованість за інвойсами.

## Перевірки
Виконано тут: 33 перевірки фактичного Java-сервісу зі спрощеними JDBC/framework замінами; 23 перевірки Vue-логіки (включно з відновленням запиту, сторно, помилкою оновлення після успішного платежу); компіляція Vue SFC; перевірка сформованих SQL-запитів на SQLite; регресія оплат закупівель (27 Java + 18 Vue) та касових операцій / звірки (38 Java). Синтаксис 445 Java-файлів розібрано парсером.

Додано 8 JUnit-тестів CashExpensesServiceTest. Повний Gradle / Spring / MySQL прогін і візуальну перевірку у браузері тут не виконано. SQLite та заміни залежностей не підтверджують MySQL DDL або реальні транзакції.

## Перевірка після встановлення
На тестовій касі: витрата 100 грн зменшує залишок на 100; сторно повертає 100; повторне надсилання не змінює залишок удруге. Перевірте фільтри та підсумки журналу, відсутність доступу менеджера, помилку при нестачі коштів і мобільний вигляд форми.
