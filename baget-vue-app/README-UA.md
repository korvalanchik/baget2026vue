# Копії нових замовлень у Telegram

Зміни поверх останньої версії з V89 (строки виконання). У ZIP лише змінені та нові файли. Каталоги backend/src і frontend/src накласти на src відповідних проєктів.

## Встановлення
1. Зробіть резервну копію БД та коду. Переконайтеся, що номер V90 вільний у вашій БД/проєкті. Застосовані міграції не змінюйте.
2. Скопіюйте файли. Запустіть бекенд: Flyway застосує V90__telegram_order_copies.sql.
3. Виконайте тести:
   .\gradlew.bat test --tests "com.example.baget.telegram.*" --tests "com.example.baget.orderproduct.*"
4. На фронтенді виконайте npm run build та оновіть розгорнуту версію.
5. Адміністратор: Налаштування → Telegram. За потреби виберіть представників фірм-посередників. Увімкніть «Надсилати копію в телеграм-бот» і натисніть «Зберегти».
6. Створіть одне тестове нове замовлення. Оновіть журнал у налаштуваннях та перевірте отримання у відповідних чатах.

## Наявне підключення
Використовуються bot.token, CHAT_ID та User.telegramId старої версії. Токен не передається на фронтенд і не входить в архів. Нових залежностей Gradle/npm немає.
Отримувачі: активний автор замовлення; усі активні адміністратори з Telegram ID; адміністративний CHAT_ID; явно вибрані активні представники фірми для замовлень RESELLER з відповідним commerce_partner_id. Роль ROLE_COUNTER сама по собі не підписує користувача. Для OWN представників посередника немає. Один chat_id отримує одну копію (незалежно від кількості правил).
Telegram ID залишаються наявними: їх створення/редагування та нова процедура прив’язки в цей етап не входять. У випадаючому списку видно, кому бракує прив’язки. Отримувач має раніше запустити наявного бота й не блокувати його. CHAT_ID адміністративного чату зберігає стару поведінку незалежно від користувацьких ролей; при зміні доступу до цього чату перевірте конфігурацію сервера.

## Поведінка
За замовчуванням прапорець вимкнений. Під час створення нового розрахованого замовлення сервер у тій самій транзакції зберігає готовий текст та чергу отримувачів. Після commit фонова задача надсилає копії. Відкат замовлення відкочує і чергу; недоступність зовнішнього Telegram не блокує збереження. Повтор create з тим самим requestKey не створює нову подію; додатково є унікальність order_no/chat_id/part_no.
Копії містять первісні розміри, кількість виробів, поля паспарту, збережені матеріали/роботи з плановою витратою та одиницями, примітки, роздрібну суму виробу і замовлення. Артикули/назви беруться з Description матеріалу без показу внутрішніх PartNo. Для посередника використовується вже розрахована роздрібна сума замовлення, не оптова та не собівартість. Відправляється звичайний текст: символи <, >, & з приміток не інтерпретуються як HTML.
Великі замовлення поділяються на частини із номером замовлення та частини. Частини одного отримувача надсилаються по порядку; помилка одного чату не блокує інші. До 5 автоматичних спроб при тимчасових помилках з паузами; для заблокованого/невідомого чату чи некоректного токена — відразу помилка. Адміністратор може повторити невдале повідомлення вручну.
Перед надсиланням перевіряються поточні прив’язки й активність отримувача. При відкликанні права його ненадіслані частини скасовуються. Нові отримувачі не додаються до старих копій.
Вимкнений прапорець зупиняє обробку існуючої черги. Після ввімкнення черга продовжиться. Замовлення, створені при вимкненій опції, не надсилаються заднім числом. Зміни існуючого замовлення на цьому етапі не створюють нової копії.
Старий POST /api/telegram/send повертає HTTP 410: довільний текст із фронтенду більше не пересилається. Актуальний Vue цей endpoint не викликає. Якщо десь залишається старий клієнт з таким викликом, приберіть його; підтримуваний маршрут — створення нового розрахованого замовлення.
Фінансові проводки, складські рухи і ціни не змінюються.

## Обмеження доставки та розгортання
Telegram sendMessage не дає ключа ідемпотентності. Якщо Telegram прийняв текст, але мережа обірвала відповідь або процес зупинився до фіксації результату, повтор може створити другу копію. Абсолютно одноразова доставка не гарантується. Запис SENT означає підтвердження API, не прочитання людиною.
Фонова задача працює, поки Spring Boot запущений та отримує процесорний час. Для Cloud Run з призупиненням CPU поза запитами потрібен режим, що забезпечує роботу фонових задач; інакше час доставки не гарантовано. Один цикл бере одне повідомлення, з блокуванням рядка; підтримано кілька екземплярів сервера.

## Перевірено тут
24 ізольовані Java-перевірки фактичного коду сервісів з підставними JDBC/framework/JSON/відправником (отримувачі, відключення, роль адміністратора, конфлікт ревізій, Unicode, черга, успіх, повтори, відкликання доступу).
11 перевірок Vue з підставним API (прапорець, отримувачі, ревізія, збереження чернетки при помилці, повтор).
4 SQL-перевірки на SQLite (порядок частин, незалежність чатів, розблокування, унікальність) без перевірки MySQL-блокувань.
Усі Vue SFC пройшли компіляцію script/template/style; 29 існуючих перевірок навігації. Java-файли пройшли синтаксичний розбір. Додано 8 JUnit-тестів TelegramCopiesTest для запуску у вашому Gradle.
Повний Gradle, MySQL/Flyway та production Vite build тут не запускалися; реальні повідомлення не надсилалися. Потрібна перевірка на вашому сервері за кроками вище.
