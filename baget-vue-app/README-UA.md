# Єдина історія замовлення та зручний пошук

Архів містить лише нові та змінені файли поверх поточної версії (після Telegram). Нова міграція БД не потрібна. Історія читає наявні таблиці; записів у фінансах, резервах чи виробництві не створює.

## Встановлення
Накладіть backend/src та frontend/src на src відповідних проєктів, зберігши резервну копію.
Бекенд:
.\gradlew.bat test --tests "com.example.baget.orderhistory.*" --tests "com.example.baget.orderproduct.*" --tests "com.example.baget.crm.*" --tests "com.example.baget.warehouse.*"
Фронтенд: npm run build. Перезапустіть бекенд та оновіть розгорнутий фронтенд.

## Де знайти
- Замовлення: спільний пошук серед усіх замовлень за точним номером, частиною імені/назви клієнта або телефоном. Номер телефону шукається без пробілів, дужок, дефісів; потрібні щонайменше три цифри телефону. Для текстового запиту — щонайменше два символи. Пошук не обмежується поточною чергою готовності та включає видані/скасовані замовлення доступних філій.
- Майстерня: той самий пошук зверху; нижче збережено окремий «Фільтр поточної дошки».
- Результат пошуку: клієнт, номер, філія, загальний стан, телефон із посиланням для дзвінка, «Відкрити замовлення» та розгортання історії. Результати можна сховати. Існуючі черги приймання, погодження та видачі залишаються на місці.
- Історія доступна без виходу з картки замовлення у Майстерні та Замовленнях, у списку замовлень клієнта CRM, а також в окремій формі видачі (зокрема за QR). У вкладених формах історія не дублюється.

## Вміст історії
Події впорядковані від нових до старих; по 50 на сторінці. Фільтри: етап і конкретний виріб/версія, включно з архівними версіями. Під час перегляду конкретного виробу загальні події замовлення, контакти та фінанси не показуються — для них виберіть «Усе замовлення».
Джерела: створення замовлення, створення/заміна версій виробів, product_production_events, production_events, product_transfers, product_price_events, reservation_events, пов’язані crm_contacts і прямо пов’язані ledger_entries.
Показуються час, дія, артикул виробу, виконавець, примітка; для переміщень — звідки/куди. Приймання з BRANCH до CUSTOMER назване «Видано клієнту». Виробничі події включають обмір, початок/зупинення/завершення, доопрацювання. Детальні таблиці обміру і матеріалів залишаються у виробничій картці.
Початок історії зі SaleDate — дата оформлення, записана в замовленні, не новий аудит. Ім’я початкового автора береться з поточного облікового запису; для створення версій, де автора історично не записували, він не вигадується. Незбережені раніше зміни/дії заднім числом не відновлюються. Поточний стан у результаті пошуку — загальний StatusOrder; конкретні вироби можуть мати різний стан.

## Доступ і фінанси
API /api/order-history/search та /api/order-history/{order} перевіряє авторизацію, активність користувача, роль і allowedBranches. Адміністратор має загальний доступ. Чужий чи відсутній номер повертає 404 без даних подій. Підставити product ID з іншого замовлення неможливо.
Майстер та склад не отримують CRM-контакти й фінанси. Менеджери власних філій бачать пов’язані проводки своїх замовлень. Для RESELLER фінансові проводки підприємства доступні тут тільки адміністратору, бухгалтеру або економісту з ROLE_ACCOUNTANT/ROLE_BOOKKEEPER та доступом до філії. ROLE_COUNTER у цьому огляді не дає доступу до фінансів підприємства для RESELLER.
Фінансова частина містить лише вибрані категорії ledger_entries з прямим order_id та відповідним branch_id. Це не розрахунок боргу чи повний журнал рахунку. Аванс клієнта, спільна оплата рахунку без прямого order_id та довідкові розрахунки клієнтів посередника не приписуються цьому замовленню. Повний фінансовий стан перевіряйте у наявній картці оплати. Фінансові JSON-знімки та собівартість в історію не передаються.
Резерви показують зміну зарезервованої кількості (до → після), а не фізичний рух складу.
Для об’єднання текстових джерел явно задана utf8mb4_unicode_ci — без зміни колації існуючих таблиць.

## Щоденна робота
Пошук виконується на сервері в доступних філіях. Результати — по 30 на сторінці. Перехід до замовлення використовує наявні форми та їхні права; можливість знайти старе замовлення не створює права його редагувати або видавати.
Історія розгортається на місці та завантажується тільки після натискання. Оновлення ручне; нові події під час перегляду можуть змістити сторінки, тому після операції натисніть «Оновити», щоб повернутися до найновіших.
Мобільний вигляд: картки без широкої таблиці, поля фільтрів в одну колонку, кнопки висотою щонайменше 44 px. Відкриття історії не скидає чернетку обміру/контакту/оплати.

## Перевірки
Пройдено 21 ізольовану Java-перевірку фактичного OrderHistoryService з підставними JDBC/framework, включно з кількістю параметрів SQL. 7 SQL-перевірок на SQLite (для перевірки вибірки та зв’язків, без MySQL CONVERT/COLLATE). 15 перевірок Vue з підставним API/renderer. 29 існуючих перевірок навігації; усі Vue SFC компілюються (script/template/style). Java-файли пройшли синтаксичний розбір.
Додано 8 JUnit-тестів OrderHistoryTest. Повний Gradle, MySQL та production Vite build тут не запускалися; візуальна перевірка в реальному браузері не виконувалася.
Ручна перевірка після встановлення: знайти власне/чуже замовлення менеджером; відкрити історію майстром; перевірити багатовирібне замовлення з погодженням, частковою видачею, архівною версією; перевірити телефон із пробілами/дужками; відкрити з CRM та за QR; перевірити на телефоні збереження доступності кнопок і відсутність горизонтальної прокрутки.
