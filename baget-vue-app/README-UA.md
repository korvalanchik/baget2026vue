# Прості управлінські показники

Зміни поверх поточної версії з єдиною історією замовлення. Лише читання даних. Нових міграцій та залежностей немає.

## Встановлення
Накладіть backend/src і frontend/src на src відповідних проєктів, попередньо зберігши резервну копію.
Бекенд:
.\gradlew.bat test --tests "com.example.baget.reports.*"
Фронтенд: npm run build. Перезапустіть бекенд та оновіть фронтенд.
Відкрити під адміністратором: Фінанси → Огляд керівника.

## Що додано
Період (до 366 днів включно, не пізніше сьогодні), філія та тип замовлень: усі / власні / посередники. Швидкі кнопки «Сьогодні», «Цей місяць». Оновлення ручне, показано застосований період та час отримання поточного стану.
За період: кількість оформлених замовлень; кількість вперше завершених позицій виробів; кількість вперше виданих клієнтам позицій. Є порівняння філій за цими трьома показниками.
Поточний стан: незавершені позиції, очікування майстра, виготовлення, минулий строк готовності, погодження ціни, дефіцит, очікування приймання на філію та готовність до видачі.
Окремий список перших 20 позицій, які мають прострочену виробничу дату, потребу погодження або дефіцит. Історія замовлення доступна на місці. Повні робочі черги залишаються в Моїх завданнях.
Адаптивні картки і фільтри для мобільного екрана; широкої обов’язкової таблиці немає.

## Правила підрахунку
Операційний огляд стосується замовлень із картками виробів нового формату (order_products). Одна картка — одна позиція; productQuantity не сумується. Статистику за кількістю примірників цей етап не додає.
Замовлення рахуються за SaleDate, включно зі згодом скасованими. Цей показник відображає факт оформлення, а не поточну активність.
Завершення — MIN(created_at) події product_production_events з action COMPLETE по виробу. Повторне COMPLETE не подвоює число. REWORK_COMPLETE не є ще одним новим виробом.
Видача — перший ACCEPT до CUSTOMER у product_transfers. Повторна видача/повернення не подвоює кількість первісних видач. Показник не є чистою кількістю після повернень.
Період застосовується до відповідної події; нові замовлення, завершення й видачі можуть стосуватися різних замовлень. Відсоток виконання з цих трьох чисел не обчислюється.
Старі завершення або видачі без збережених подій не відновлюються. Для результатів за період історичні події не відкидаються через поточний active/status.
Часові межі періоду: початок першого дня включно, початок наступного за останнім дня виключно, Europe/Kyiv.
Тип OWN/RESELLER береться з історично збереженого commerce_mode замовлення. Невизначений тип входить тільки до «Усі» і має власну позначку в порівнянні філій.

Поточні черги не залежать від вибраного періоду, але враховують філію/тип. Враховуються активні вироби та замовлення без StatusOrder 5/10. Незавершені: WAITING, ACCEPTED, IN_PROGRESS, PAUSED, які не у клієнта. STOPPED не входить у цей показник.
Минув строк готовності: ShipDate раніше сьогодні, тільки в незавершеній черзі. Для готових виробів, що очікують клієнта, така позначка не застосовується.
Погодження: WAITING/REJECTED у product_price_approval. Дефіцит: існує активний material_reservations з demand > reserved. Кілька дефіцитних матеріалів одного виробу рахуються як одна проблемна позиція. Погодження/дефіцит у цьому огляді стосуються незавершеної черги.
Готові до видачі: COMPLETED + підтверджено, BRANCH, немає pending_location та активного доопрацювання.
Очікують філію: COMPLETED із pending_location BRANCH.
Черги перетинаються, їх не можна підсумовувати як окремі незалежні групи.

## Фінансовий блок
Використано чинний OwnerResultsService.report: та сама логіка, що у «Звіти → Власні філії». Нової паралельної формули немає, фінансові поля orders не використовуються.
За першою видачею у вибраному періоді: відомі суми реалізації, відома собівартість матеріалів, нараховані винагороди та різниця після них. Якщо є невизначені ціни, собівартість або винагороди, показано кількість неповних позицій і різницю «Не визначено». Частково відомі суми не видаються за повні.
Це не чистий прибуток і не касовий залишок: оренда, комунальні та інші витрати тут не відняті. Гроші кінцевих клієнтів посередника не включаються. Оплати, перекази кас і розрахунки з фірмами залишаються у своїх наявних звітах.
При фільтрі RESELLER фінансовий блок власних філій не запитується. При ALL він окремо й явно показує лише OWN, у межах обраної філії та дат. Якщо філія має історично різні типи, береться тип конкретного замовлення.
Обмеження існуючого фінансового звіту (понад 10000 виробів) показується як помилка цього блоку: для нього треба зменшити період. Операційні показники при такій помилці лишаються доступними.

## Доступ
Лише активний ROLE_ADMIN. Це перевірено сервером; приховування вкладки не є єдиним захистом. Решта ролей не отримують доступу через прямий URL.
API: GET /api/reports/management-overview/branches та GET /api/reports/management-overview?from=YYYY-MM-DD&to=YYYY-MM-DD&branch=...&mode=ALL|OWN|RESELLER.

## Перевірки
18 ізольованих перевірок фактичного Java-сервісу з підставними JDBC/framework та викликом-замінником існуючого фінансового звіту. Включають права, межі періоду, параметри SQL, тип/філію, відсутність виклику OWN для RESELLER та обмеження списку уваги.
7 перевірок фактичних запитів на SQLite: перші події, повторні події, різні філії/типи, скасування, дублікати дефіциту, черги готовності. Це не MySQL integration.
14 перевірок Vue з підставним API/renderer та 29 регресійних перевірок навігації. Усі Vue SFC компілюються (script/template/style); Java-файли синтаксично розібрано. Додано 5 JUnit-тестів ManagementOverviewTest.
Повний Gradle, MySQL та production Vite build тут не запускалися, браузерна перевірка макета не виконувалась.
Після встановлення звірте кілька відомих замовлень із періодом та оглядом, а фінансові числа — з «Звіти → Власні філії» за тими самими датами/філією. Перевірте адміністратора, звичайного менеджера й мобільний екран.
