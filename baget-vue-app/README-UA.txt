ЗАМОВЛЕННЯ: ПРИЙМАННЯ НА ФІЛІЮ ТА ВИДАЧА

Встановити поверх останнього пакета CRM з історією виданих замовлень та мобільними картками оплати.
Скопіювати backend/src і frontend/src у відповідні проєкти із заміною. Перезапустити backend, виконати npm run build для production frontend. Нових міграцій БД немає.

Вкладка «Замовлення» містить три розділи: погодження цін, очікування приймання на філію, готові до видачі.
Пошук за точним номером працює незалежно від розділу, включно з уже виданими замовленнями. QR/посилання відкриває замовлення відповідного виробу. Доступ обмежений дозволеними філіями; адміністратор бачить усі.
Приймання: позначити фактично отримані вироби й натиснути «Прийняти вибрані на філію». Кожен виріб проводиться існуючою операцією з перевіркою версії та записом історії. Кілька вибраних виробів приймаються послідовно, НЕ однією атомарною транзакцією. Якщо помилка виникла посередині, вже прийняті залишаються прийнятими, форма показує успіхи й перечитує стан. При втраті відповіді перевірте оновлену картку перед повторенням.
Видача: використовується та сама CrmIssuePanel, що у CRM — клієнт, рахунок, аванс, доплата, потім окреме підтвердження видачі. Збережено довідковий облік посередника та фінансові обмеження. Замовлення може одночасно бути у списках приймання й видачі, якщо різні його вироби знаходяться на різних етапах.
Готові до видачі означає фізично готові й прийняті на філію; оплата/борг перевіряються у картці. Старі замовлення без OrderProduct можна знайти, але приймання та видача нового формату для них недоступні.

Перевірки тут: 15 перевірок Vue з імітованим API (пошук, часткове приймання, помилка другої позиції, повторення, QR, блокування переходів); компіляція нового SFC; ESLint нового компонента й App.vue; синтаксичний розбір Java.
Додано JUnit-перевірки обмеження доступу до іншої філії, порожнього доступу й параметрів запиту. Повний Gradle/JUnit, MySQL і браузерний прогін тут НЕ виконані.

На вашому ПК:
.\gradlew.bat test --tests "com.example.baget.warehouse.*" --tests "com.example.baget.crm.*"
npm run build (у frontend)

Ручна перевірка: менеджер своєї філії → приймання частини замовлення → решта залишається у черзі → оплата/аванс → видача частини → пошук повністю виданого замовлення за номером. Перевірити також недоступну філію, QR, скасоване замовлення, зміну стану іншим менеджером.
