# V67 — типи філій, два розрахунки та погодження понад 5%

Перший узгоджений етап нової моделі. Архів містить тільки зміни поверх V66. Включено виправлення циклу branches у CustomerCreditService, яке раніше виконували вручну.

## Встановлення й початкове налаштування

1. Перенесіть backend/src та frontend/src у відповідні src проєктів. Скопіюйте нові тести.
2. Додайте V67__branch_pricing_approval.sql. Старі застосовані міграції не змінюйте.
3. Запустіть тести, бекенд із Flyway та фронтенд.
4. Адміністратором відкрийте CRM → «Філії / погодження ціни перед виготовленням» → «Налаштування прайсів філій».
5. Кожній філії призначте «Своя» або «Філія реселлера». Для реселлера вкажіть код фірми з довідника клієнтів. Пошук за телефоном допоможе знайти код. Фірму спочатку потрібно мати в довіднику клієнтів.
6. Запишіть причину зміни й збережіть налаштування кожної філії.

До явного налаштування філії новий розрахунок через нову форму і створення нового замовлення блокуються. Міграція навмисно не вгадує власника філії за ролями її менеджера.

## Прайси

- OWN: роздріб ListPrice.
- RESELLER: роздріб кінцевого клієнта ListPrice_3, паралельна вартість для фірми за ListPrice_1.
- Cost не підміняє роздрібну ціну, навіть якщо нове замовлення оформляє адміністратор.
- ListPrice_2 не використовується.

Тип філії та фірма фіксуються у замовленні. Ціни одиниці фіксуються в позиціях. Зміна налаштувань філії або поточного каталогу не переоцінює вже збережений обмір. Новий preview для відкритого замовлення використовує збережений тип філії.

Як і раніше, явне редагування та повторне збереження конфігурації замовлення ДО його приймання у майстерню створює нову версію виробів за актуальними цінами. Після приймання цей шлях закритий.

Для нових виробів зберігаються початкова роздрібна сума, початковий паралельний розрахунок і після обміру — поточні роздрібна та реселлерська суми. Реселлерський розрахунок видно в картці перевірки ціни. Він поки не є виставленим рахунком чи боргом.

## Майстерня

Приймання від філії дозволене без погодження. До початку виготовлення майстер має зберегти обмір та фактичні витрати. Використовується наявний розрахунок витрат за обміром; ручні уточнення фактичної кількості також враховуються.

Порівняння для кожного OrderProduct, включно з його кількістю екземплярів:

abs(поточна роздрібна сума − початкова роздрібна сума) × 100 > початкова роздрібна сума × 5

Рівно ±5% проходить автоматично. Порівняння точне через BigDecimal, без округлення відсотка. Якщо початкова ціна 0, то 0 → 0 проходить, а будь-яке додатне нарахування потребує погодження.

Стани перевірки:

- UNMEASURED — обмір не збережено; початок роботи заблокований.
- AUTO — відхилення не перевищує 5%; можна починати.
- WAITING — потрібне погодження; виготовлення заблоковане.
- APPROVED — менеджер погодив поточний розрахунок.
- REJECTED — повернуто на уточнення; виготовлення заблоковане.

Контроль виконується сервером при переході IN_PROGRESS і при завершенні. Старий API роботи з усім замовленням не дозволяє обійти контроль для нових замовлень цієї моделі.

Якщо новий збережений обмір виробу, що вже перебуває IN_PROGRESS, виходить за коридор, сервер повертає його в ACCEPTED і ставить WAITING. Списання матеріалів при цьому не відбувається. Новий запуск потребує погодження. Інші вироби замовлення можуть працювати незалежно.

Погодження прив'язане до відбитка обміру, позицій, кількостей і зафіксованих цін. Зміна розрахунку запускає перевірку повторно від незмінної початкової роздрібної суми; старе погодження не переноситься. Повторне збереження ідентичного розрахунку його не скидає.

## Дії менеджера

CRM → «Філії / погодження ціни перед виготовленням» показує вироби WAITING та REJECTED з дозволених філій. Менеджер записує результат домовленості й обирає «Клієнт погодив нову ціну» або «Повернути на уточнення».

Погоджувати можуть ADMIN, MANAGER, SELLER, LEVEL2, COUNTER у межах доступних філій. FOREMAN без додаткової менеджерської ролі погоджувати не може. Налаштовувати типи філій може лише ADMIN.

Рішення, працівник, причина та знімок розрахунку зберігаються в історії. Виріб REJECTED можна погодити після повторного обговорення без зміни ціни; якщо майстер змінює розрахунок, погоджується нова версія. Погодження не запускає виготовлення автоматично: майстер оновлює картку й натискає початок роботи.

## Межі цього етапу

Старі замовлення не класифікуються автоматично і не отримують заднім числом нові базові суми/правило 5%. Для перевірки нового процесу створіть нове замовлення після налаштування філії.

Цей етап не додає нового редактора складу виробу в майстерні: залишаються чинні можливості обміру й витрат. Якщо розрахунок за обміром вимагає іншого артикула/нової позиції, чинна перевірка складу продовжує вимагати окремого узгодження; автоматичної підміни матеріалу немає.

Наступний узгоджений етап — рахунки фірмі за реселлерською ціною, окремий довідковий журнал грошей посередника й адаптація видачі. Тут навмисно не створюється борг фірми автоматично.

Щоб поточні фінансові форми не провели неправильні операції:

- старі шляхи виставлення рахунку за роздрібною сумою для нових RESELLER-замовлень блокуються;
- приймання авансу/оплати через InvoiceSettlementService від філії, налаштованої як RESELLER, блокується з поясненням;
- власні філії продовжують чинний фінансовий процес;
- історичні платежі та ledger_entries автоматично не змінюються.

Тому повний цикл реселлерського замовлення до рахунку/видачі ще не слід переводити на цю модель в робочому обліку: зараз перевіряємо налаштування, розрахунки та погодження у тестовому середовищі. Повноцінне розділення фінансів — наступний етап.

## Перевірка

У корені бекенду:

```powershell
.\gradlew.bat test
```

Або цільовий набір:

```powershell
.\gradlew.bat test --tests "com.example.baget.commercial.*" --tests "com.example.baget.calculation.*" --tests "com.example.baget.orderproduct.*" --tests "com.example.baget.finance.*" --tests "com.example.baget.billing.*"
```

У Vue:

```powershell
npm run build
```

Ручний сценарій:

1. Налаштувати власну та реселлерську філії.
2. Один склад виробу має різну роздрібну ціну відповідно до ListPrice і ListPrice_3; для реселлера видно також суму ListPrice_1.
3. Прийняти виріб; спроба почати до збереження обміру має відхилитися.
4. Для початкових 1000 грн перевірити 950 і 1050 — без погодження; 949.99 і 1050.01 — WAITING.
5. Майстром спробувати погодити ціну — відмова. Менеджером чужої філії — відмова.
6. Менеджером своєї філії погодити ціну; майстром оновити картку й почати роботу.
7. Змінити витрати — перевірка запускається повторно. Вихід понад 5% зупиняє виготовлення.
8. Перевірити, що інший виріб цього замовлення може виготовлятися незалежно.

Виконано локально: 60 перевірок скомпільованого PriceTolerance, 14 наявних Node-тестів платежів/UUID, ESLint, компіляцію 5 Vue SFC, синтаксичну перевірку Java та кількість параметрів у 72 SQL-викликах CommercialService/CalculatedOrderService/WorkshopService.

Додано 13 JUnit-сценаріїв; підготовку WorkshopServiceTest оновлено для нової залежності. Повний Gradle/JUnit та MySQL/Flyway тут не запускалися. Перевірка синтаксису не є повною компіляцією Spring-проєкту.
