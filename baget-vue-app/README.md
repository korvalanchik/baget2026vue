# V66 — видача з відстрочкою та контроль оплати

Зміни поверх V65. Усі попередні міграції, фінансові процесори та аванси залишаються чинними.

## Встановлення

1. Перенесіть backend/src у src бекенду, frontend/src у src Vue-проєкту.
2. Додайте міграцію V66__customer_credit.sql. Не змінюйте вже застосовані V65 та попередні міграції.
3. Запустіть тести, потім бекенд для застосування Flyway та оновіть фронтенд.

```powershell
.\gradlew.bat test --tests "com.example.baget.finance.*" --tests "com.example.baget.billing.*" --tests "com.example.baget.warehouse.*" --tests "com.example.baget.crm.*"
```

```powershell
npm run build
node --test tests/customer-payment.test.mjs tests/request-key.test.mjs
```

## Де працювати

У CRM відкрийте картку клієнта: розділ «Відстрочка оплати». Він також є у фінансовому блоці клієнта, зокрема при видачі виробу на філії.

Адміністратор / бухгалтер (ADMIN, COUNTER, ACCOUNTANT, BOOKKEEPER):

- вводить причину або погоджену домовленість;
- дозволяє чи відкликає «Видачу з відстрочкою» для клієнта у вибраній філії;
- встановлює дату оплати конкретного відкритого рахунку і натискає «Зберегти дату рахунку».

Менеджер бачить умови, але не може змінювати їх. Ознака «Партнер» сама по собі не дає дозволу. Для редагування строку об'єднаного рахунку потрібні бухгалтерські права та доступ до всіх його філій. Дата належить усьому рахунку, а дозвіл на видачу — клієнту у конкретній філії.

Для нового об'єднаного рахунку після злиття дату потрібно погодити окремо: дати старих рахунків автоматично не переносяться.

## Видача

Для оплаченого чинного рахунку дозвіл і дата не потрібні.

Для видачі з боргом одночасно потрібні:

- чинний остаточний рахунок за виріб;
- явний дозвіл для клієнта рахунку у філії замовлення;
- дата оплати рахунку.

Умови перевіряються сервером під час SEND і ACCEPT. Відкликання дозволу або вилучення дати між цими діями блокує підтвердження неоплаченої видачі. Оплата рахунку дозволяє завершити видачу без відстрочки.

Дата, що минула, показує прострочення, але не відкликає дозвіл автоматично. Бухгалтер може відкликати його явно. Нові заборони не повертають уже видані вироби.

Журнал фіксує окремо підготовку передачі та підтвердження видачі: виріб, рахунок, філію, працівника, дату, борг на момент дії, строк оплати та версії дозволу/умов. Він доступний у розділі відстрочки. Зміни дозволу та дати теж мають історію з причиною.

Видача не створює жодного платежу, алокації авансу або фінансової проводки. Борг погашається тільки наявними фінансовими операціями.

## CRM

Кнопка «Очікується оплата / Прострочено» відкриває список чинних рахунків із боргом та фільтр філії.

- «Очікується оплата» включає всі чинні неоплачені рахунки, у тому числі без дати й прострочені.
- «Прострочено» включає рахунки з боргом і датою раніше сьогоднішньої за Europe/Kyiv. Дата означає «сплатити до цього дня включно».
- Після повної оплати рахунок зникає з обох списків при оновленні. Частково оплачений залишається з поточним боргом.
- Через «Картка клієнта / записати контакт» відкривається наявна картка CRM, а рахунок підставляється у запис контакту. Дзвінки та примітки зберігаються у чинній історії CRM.
- Об'єднаний рахунок може бути показаний у кожній пов'язаній філії. Його повний борг повторюється, тому між такими рядками не потрібно підсумовувати суму.

## Перевірка вручну

На тестовому рахунку з боргом:

1. Без дозволу і дати видача заборонена.
2. Встановити тільки дозвіл — видача ще заборонена.
3. Встановити дату — передача і підтвердження видачі дозволені; сума боргу не змінюється.
4. Переглянути історію: SEND означає підготовку, ACCEPT — фактичне підтвердження видачі.
5. На іншому виробі після SEND відкликати дозвіл, потім спробувати ACCEPT — сервер має відмовити.
6. Установити вчорашню дату — рахунок з'явиться у «Прострочено». Сам дозвіл залишиться чинним.
7. Частково оплатити — борг зменшиться; після повної оплати рядок зникне зі списку при оновленні.
8. Менеджером спробувати змінити умови через POST напряму — сервер має відмовити.
9. Перевірити філію без доступу та спробу редагування рахунку іншого клієнта.

## Перевірки

Виконано: 20 окремих перевірок скомпільованого Java CreditRules, 14 наявних Node-тестів сум/UUID, ESLint, компіляцію 5 Vue SFC, перевірку синтаксису Java та 22 SQL-викликів за кількістю параметрів.

Додано 11 JUnit-сценаріїв для правил, доступу, повторного збереження, застарілої версії та фіксації видачі з боргом. Оновлено підготовку наявних тестів.

Повний Gradle/JUnit, запуск Spring та MySQL/Flyway у цьому середовищі не виконувалися. Команди вище потрібно виконати у вашому проєкті.

Список боргів використовує InvoiceFinanceService для поточного боргу та фільтрує результати до розбиття на сторінки. Для невеликого проєкту це зберігає єдиний розрахунок боргу; за значного зростання кількості відкритих рахунків цей запит слід оптимізувати. Строк оплати цього етапу відображається в інтерфейсі CRM; шаблон PDF рахунку не змінюється.
