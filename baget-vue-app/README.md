# Картка руху матеріалу — етап 63
Встановлюється поверх V62. Нової SQL-міграції немає.

## Встановлення
Скопіюйте ВМІСТ backend/ до кореня Java-проєкту (де gradlew.bat),
ВМІСТ frontend/ до кореня Vue-проєкту (де package.json).
Не створюйте вкладені backend/backend або frontend/frontend.
Архів додатково включає StocktakeService з виправленими П'ЯТЬМА параметрами event()
та його регресійним тестом, щоб помилка попереднього V62 не повернулася.

Перезапустіть бекенд після збірки.
    .\gradlew.bat test --tests "com.example.baget.warehouse.*" --tests "com.example.baget.stocktake.*"
    node --test tests/material-card.test.mjs
    npm run build

## Де знайти
Матеріали → Залишки та інвентаризація → вибрати матеріал → Картка руху матеріалу.

Показники: фізичний залишок, резерв, вільний залишок, загальна активна потреба,
незабезпечена потреба, очікувані поставки ORDERED/PARTIAL.
Чернетки й закриті замовлення постачальнику не включаються в очікування.
Майбутня поставка не збільшує фізичний чи вільний залишок.

Єдина історія: прихід, COUNT, виробничі списання, переробка, резерви.
Для резервів «до/після» означає резерв, для інших подій — фізичний залишок.
NULL до інвентаризації означає невідомий початковий залишок і невідому різницю.
Історія охоплює лише наявні журнали; заднім числом рухи не відновлюються.
Старі події потреби зберігали тільки зміни резерву: історичні величини потреби не вигадуються.

Фільтри: від/до включно, тип. До 100 рядків на сторінці; CSV саме поточної сторінки.
Поточні показники не є залишком на кінець вибраного періоду.
Кожен запит читає узгоджений знімок REPEATABLE_READ; між сторінками нові операції
можуть змістити записи. Це не незмінний аудиторський експорт.
Однаковий час двох подій не визначає їх фактичний порядок.

Переходи: акт і постачання відкриваються у відповідних вкладках.
Замовлення відкриває перелік позицій саме вибраного матеріалу, план/факт і розміри.
Виріб відкривається нижче картки в наявному перегляді переміщення,
з вимкненими операціями переміщення. Неактивний виріб може бути недоступний
за чинними правилами існуючого endpoint; історія матеріалу лишається доступною.
Доступ до картки: чинні ролі ADMIN/FOREMAN/WAREHOUSE, спільний склад.

## Перевірки
Пройшли 4 Node-тести, ESLint, компіляція 4 Vue SFC і синтаксичний розбір Java.
На SQLite-фікстурі виконана реальна UNION-вибірка (допоміжні MySQL IF/CONCAT
емульовані): перевірено типи подій, документи, невідомий залишок, ізоляцію матеріалів.
Це не перевірка MySQL.
Додані 3 JUnit-тести: відмова доступу, некоректні дати, параметри/пагінація/NULL.
Повні Gradle-тести, Spring, MySQL і ручний браузерний сценарій тут не запускалися.

## Локальні сценарії
1. Матеріал з NULL: невідомий залишок і вільна кількість, не нулі.
2. Прихід за поставкою: один запис, правильні посилання й номер накладної.
3. Інвентаризація: до/після і різниця; акт відкривається.
4. Виробництво/переробка: різні типи, від'ємна витрата, правильні замовлення/вироби.
5. Резерв: зміна резерву, не фізичного залишку.
6. Межі дат: обидва календарні дні включаються.
7. Понад 100 подій: наступна сторінка і CSV відповідають фільтру.
8. Неавторизований користувач не отримує історію через прямий API.
9. Повторне оновлення картки не змінює склад, резерви чи фінанси.
