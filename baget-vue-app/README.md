# CRM — перший етап, міграція V63
Накладається поверх етапу 63 «Картка руху матеріалу».
Етап 63 не мав міграції; тому наступний номер Flyway тут — V63.

## Встановлення
Вміст backend/ скопіюйте до кореня Java-проєкту, де gradlew.bat.
Вміст frontend/ скопіюйте до кореня Vue-проєкту, де package.json.
Не залишайте зайву вкладену папку backend або frontend.
Запустіть локально:
    .\gradlew.bat test --tests "com.example.baget.crm.*"
    node --test tests/crm.test.mjs
    npm run build
Перезапустіть бекенд: Flyway створить дві CRM-таблиці.
Оновіть сторінку фронтенду; права меню перераховуються із збережених ролей.
Якщо серверні ролі змінювалися, увійдіть заново.

## Що додано
Меню «Клієнти CRM», три вкладки:
- Замовлення в роботі.
- Очікують видачі.
- Партнери / рахунки.

Нові вироби групуються за production_state і current_location.
COMPLETED до передачі CUSTOMER — готовий, незалежно від оплати.
Скасовані замовлення (5,10) виключено з виробничих списків.
WAITING/ACCEPTED/IN_PROGRESS/PAUSED — незавершені вироби.
Можливе одночасне потрапляння клієнта до кількох вкладок.
Для старих замовлень без активних OrderProduct:
0,1,2 — у роботі; 3,4,6,7,8,9,11 — кандидати на видачу.
У картці такі замовлення явно позначено як старі з потребою уточнення готовності.
Це сумісність зі старими статусами, а не підтвердження фізичного місця видачі.

Клієнт показаний окремо для кожної доступної філії.
Контактна історія, наступна дата та ознака партнера прив'язані до філії.
Той самий клієнт на іншій філії має власну історію і домовленість.
Доступ перевіряється на сервері через allowedBranches навіть для адміністратора.
Ролі CRM: ADMIN, COUNTER, ACCOUNTANT, BOOKKEEPER, MANAGER, SELLER, LEVEL2, FOREMAN.
Права фінансових кнопок залишено як раніше: додаткових ролей для оплат не надається.

Пошук: ім'я, телефон (також без пробілів/дужок), точний номер замовлення.
Позначка «Шукати серед усіх клієнтів філії» дозволяє знайти клієнта поза вкладкою.
Вона охоплює клієнтів, пов'язаних із замовленнями або рахунками філії, включно з платником.
Нових клієнтів без замовлень/рахунків ця форма поки не створює.
Партнерів не виводимо автоматично з факту об'єднання рахунків:
знайдіть клієнта через «усіх», відкрийте картку і позначте партнером.
Список партнерів спочатку може бути порожнім.

## Контакти
Повідомлено, Не відповів, Передзвонити, Домовленість, Примітка, Домовленість завершено.
Текст, дата наступного контакту, необов'язкове замовлення або рахунок.
Автор і час додаються сервером. Записи не перезаписуються і не видаляються.
Помилку можна уточнити наступною приміткою.
CALL_BACK вимагає дату, DONE очищує поточне нагадування.
Звичайна примітка зберігає поточну дату, доки її явно не змінено.
Історія зберігає попередні домовленості.
Фільтр «Контакт сьогодні або прострочений» використовує календарний день Europe/Kyiv.
Автоматичних дзвінків, повідомлень або зовнішніх нагадувань немає.
Натискання tel: саме по собі не записує успішний контакт.
Перед виходом із незбереженої картки є підтвердження; автозбереження немає.

Ключ операції захищає від дублювання при повторі того самого запиту.
Оновлення профілю серіалізовано блокуванням клієнта і expectedRevision.
При конфлікті оновіть картку: система не перезаписує чужу домовленість мовчки.
Фінанси, склад, статуси замовлень і виробів контактами не змінюються.

## Межі першого етапу
Список — 50 клієнтів/філій на сторінці; історія — 50 записів на сторінці.
Картка показує до 200 останніх позицій замовлень і 200 рахунків, з попередженням про ліміт.
Фінансовий екран та API оплат збережено; фінанси в ньому, як раніше, за клієнтом загалом.
Філія нової оплати/авансу береться з відкритої CRM-картки.
Цей етап не переписує старий фінансовий API та його модель доступу.
Існуючі коментарі платежів залишаються у фінансовій історії, нові контакти — в CRM.
Ознака партнера не створює рахунок і не змінює платника.

## Перевірки
Пройшли 7 Node-тестів, ESLint змінених компонентів/модулів,
компіляція Vue SFC (CRM, фінансовий екран, App), синтаксичний розбір Java.
Перевірено кількість параметрів 12 літеральних SQL-викликів JDBC.
SQL списків виконано на SQLite-фікстурі з емуляцією функцій MySQL:
часткова/оплачена/стара готовність, видані/скасовані, ізоляція філій,
партнер-платник, телефон/номер замовлення, наступна дата та останній контакт.
Це не перевірка MySQL.
Додані 8 JUnit-тестів: доступ, відсутній зв'язок, ревізія, дата,
параметри запису, повторний ключ, конфлікт ключа, чужий документ.
Gradle/JUnit, Flyway на MySQL і ручний браузерний сценарій тут не запускалися.

## Що перевірити локально
1. Нове замовлення — клієнт у роботі.
2. Один виріб готовий, інший ні — клієнт у двох вкладках, часткова готовність у картці.
3. Оплачений готовий виріб лишається до видачі CUSTOMER.
4. Місце та очікувана передача відповідають майстерні/складу/філії.
5. Два контакти різних працівників зберігають автора/час.
6. Наступний дзвінок потрапляє в due-фільтр; DONE прибирає його, не стираючи історію.
7. Дві відкриті картки: друга застаріла зміна дає конфлікт ревізії.
8. Повтор однакового POST з тим самим ключем не додає контакт вдруге.
9. Чужа філія, замовлення чи рахунок не допускаються.
10. Позначення партнера діє тільки у вибраній філії.
11. Фінансовий екран відкривається з правильною філією для платежу.
